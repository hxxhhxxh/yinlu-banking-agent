# 银枢·AI银行副驾 —— 方案正文

> 版本：v1.0（2026-09-22）　作品类型：面向青年客群的手机银行 AI 智能体
> 关键词：AI Agent、安全合规、分级授权、适当性管理、跨场景服务编排

---

## 一、项目概述

### 1.1 一句话价值

**让用户用一句大白话办完银行业务，同时让每一步资金变动都安全、可解释、可追溯。**

### 1.2 产品形态

"银枢·AI银行副驾"包含两部分：

- **左侧智能对话区**：用户用自然语言表达金融意图，AI 实时展示"思考 → 规划 → 调用工具 → 结果反馈"的完整过程。
- **右侧仿真手机银行**：卡片、账单与异常识别、订阅与代扣、理财与持仓、卡片业务、安全中心随对话实时联动。

所有数据为本地沙箱数据，不接入任何真实支付、银行或商户接口。

### 1.3 设计出发点

青年用户是手机银行的高频使用者，却也是电信诈骗与不当理财的主要受害群体。他们需要的不只是"更方便的入口"，而是**"更方便，但关键处有人替我把关"**。因此本方案把 AI 的能力用在两件事上：把复杂流程压缩成一句话，把风险判断前置到资金变动之前。

## 二、行业背景与痛点

| 痛点 | 具体表现 | 本作品的应对 |
| --- | --- | --- |
| 入口深、操作碎 | 转账要找收款人、填金额、选卡、看限额；理财要读多页条款 | 一句话完成，参数由 Agent 从上下文抽取 |
| 风险提示形同虚设 | 弹窗一划而过，用户不读条款 | 关键信息以结构化卡片呈现，达到门槛必须验证码确认 |
| 适当性执行靠人 | 线下靠客户经理判断，线上靠客户自己"点过风险确认" | 由系统强制过滤，超等级产品不推荐也不可申购 |
| 诈骗识别滞后 | 事后才发现被骗 | 收款人白名单、涉诈黑名单、夜间大额、整数大额等 10 条规则事前拦截 |
| 操作难以追溯 | 出问题后难复盘 | 六类操作全部留痕，含风险等级、原始请求与执行理由 |
| 客户"被静默续费" | 订阅扣费不透明 | 从流水自动识别周期扣费、续费倒计时提醒、一键取消 |

## 三、产品设计

### 3.1 六大核心场景

**场景一：智能转账**

- 收款人识别支持：姓名、昵称（我妈/室友/房东）、手机号尾号、备注线索；无法确定时不猜，反问用户。
- 转账前强制展示：收款人、开户行、脱敏账号、金额、付款卡、命中的风控规则。
- 扩展能力：定时转账（每月某日）、AA 拆分收款（按人数平摊并生成待收清单）、T+0 撤销最近一笔转账（资金原路返回，超当日明确拒绝并指引柜面）。

**场景二：账单分析**

- 消费分类统计（占比、笔数、笔均）、环比上期、消费时段分布、商户榜、最大单笔。
- 年度报告：全年收支、月均/日均、最高与最低月份、分类占比。
- **异常交易识别（评分制）**：深夜大额、异地交易、境外交易、金额突增（相对同分类中位数）、超大额五类特征累加打分，≥40 分列入异常，每笔给出风险分与多条可核对证据。实测在 303 笔支出中独立复现数据里预埋的全部 4 笔异常，零误报。

**场景三：理财操作**

- 风险测评：5 题问卷（年龄、收入、资金占比、投资经验、亏损承受度），总分映射 C1（保守型）~ C5（进取型），有效期一年。
- 适当性过滤：以产品可售名单为权威依据，超等级产品从推荐中消失、也不可申购，并在回答中明确说明"收益再高也不会推荐"。
- 申购/赎回：三道门校验（测评有效性 → 适当性 → 起购金额与余额），确认卡片内嵌风险揭示并提供**风险提示朗读**；沙箱按 T+0 到账并在回执中标注真实环境为 T+1。

**场景四：卡片管理**

- 卡片申请：确认后生成受理单，状态"审核中（1–3 个工作日）"，不假装已发卡。
- 额度调整：校验单卡上限与已用额度，变更后可用额度同步重算。
- 交易限额/冻结：单笔与日累计限额校验；冻结即刻生效，可自助解冻。
- 卡片挂失：确认后立即冻结并标记"已挂失·不可恢复"，返回含受理编号的回执，不可自助解冻。

**场景五：订阅/代扣管理**

- 从真实流水中按"金额固定 + 间隔稳定（约 30 天）+ 出现≥3 次"自动识别周期扣费，并给出识别依据。
- 年度型订阅（一年仅扣一次）由已登记信息提供，明确标注"已登记"而非"已自动识别"——不夸大识别能力。
- 续费提前提醒（含剩余天数）与一键取消，取消后不再自动扣费。

**场景六：跨场景联动**

- 一句"下周我妈生日"：识别对象、场合，主动补问日期、预算与偏好（一次问全，不逐步骚扰）。
- 在预算内挑选总价最高的组合（¥500 预算 → 玫瑰礼盒 ¥268 + 6 寸慕斯 ¥218 = ¥486，余 ¥14 预留运费）。
- 执行时序：**锁定资金 → 逐笔下单 → 释放剩余 → 生成配送提醒**，金额完全守恒，并生成提前一天的配送确认提醒。

### 3.2 交互设计

- **过程可见**：每个意图与工具调用都以时间线呈现，每步可展开"为什么这么做"。
- **确认即卡片**：待确认操作以卡片形式展示关键信息，含风险提示、验证码输入、朗读按钮与取消入口；也可直接在对话里回复"确认"。
- **实时联动**：对话查到什么，右侧就显示什么（查询结果整批联动、卡片高亮、异常卡片定位）。
- **状态保留**：刷新与重启后，对话、订单、持仓、订阅状态全部保留。

## 四、安全与合规体系

### 4.1 分级授权

| 级别 | 覆盖操作 | 处理方式 |
| --- | --- | --- |
| 🟢 绿色·自动执行 | 查询类（余额、明细、账单、订阅、持仓、收益查询、风控预检） | 确认意图后直接执行，写审计 |
| 🟡 黄色·用户确认 | 小额转账（**当日累计 ≤ ¥1,000**）、订阅取消、**虚拟卡申请**、交易限额、冻结/解冻、实体卡申请 | 展示关键信息 + 点击确认 |
| 🔴 红色·多因子强验证 | 大额转账（**当日累计 > ¥1,000**）、**交易密码修改**、卡片**挂失/解挂**、理财申购与赎回、额度调整 | 展示关键信息 + **短信验证码 + 人脸识别**（沙箱模拟）；红色操作**不能在对话里用“确认”代替** |
| 阻断级（涉诈黑名单） | 任意金额 | **直接拦截，不提供确认入口**，提示拨打 96110 |
| 业务拒绝（收款人不存在、余额不足、超限额、适当性不符、测评过期） | —— | 拒绝并给出原因与差额，明确"未发生任何资金变动" |

字段说明：分级由 `securityGuard.classifyTier` 统一判定，转账按**当日累计**（今日已完成转账之和 + 本笔）而非单笔金额；分级依据在界面上直接可见。

### 4.2 风控规则引擎（10 条）

R-01 收款人不在常用名单 · R-02 收款账户涉诈黑名单 · R-03 金额达到二次确认阈值 · R-04 夜间大额 · R-05 整数大额 · R-06 可用余额不足 · R-07 超单笔限额 · R-08 超当日累计限额 · R-09 收款人不存在 · R-10 备注命中高风险话术（刷单、保证金、安全账户、催促话术等）。

规则目录是规则数量的唯一来源，验收脚本会校验"对外声明的条数 = 实际执行条数"，从机制上防止出现写死的规则数量。

### 4.3 适当性管理

先测评、再适当性、才推荐；不匹配即拒绝，拒绝动作写入审计（可追溯"系统为何不卖"）。降为 C1 保守型后，可推荐产品立即收缩，且申购 R2 产品会被直接拦截。

### 4.4 全程留痕

成功、未就绪、失败、拒绝、取消、未识别意图六类操作全部写入本地操作日志，含操作名、风险等级、金额、原始请求与执行理由；审计编号在进程重启后连续不重号。

### 4.5 知情同意与边界管理

每一步敏感操作都提供"为什么这么做"的解释入口；对沙箱与真实环境的差异（模拟验证码、赎回 T+0 加速、办卡仅到审核中）在界面与回执中明确标注。

## 五、技术架构

```
浏览器（原生 HTML / CSS / JS，无框架依赖）
  ├─ 左：对话区（Agent 过程时间线 + 流式回答 + 待确认卡片）
  └─ 右：仿真手机银行（卡片/账单/理财/安全中心）
        │  fetch + SSE 流式事件
        ▼
Node.js 零依赖后端（仅监听 127.0.0.1，单命令启动）
  ├─ store.js        状态仓库（内存 + 落盘 + 全程留痕 + 对话持久化）
  ├─ data/mockdata.js 确定性种子生成的沙箱数据（可复现）
  └─ agent/
       ├─ orchestrator.js  编排器：意图 → 规划 → 工具 → 确认 → 反馈（事件流）
       ├─ tools.js         25 个银行工具（含风险等级与是否需二次确认）
       ├─ actions.js       动作层：待确认单/验证码/执行/取消（真实扣款只在这里）
       ├─ riskEngine.js    风控规则引擎（10 条规则 + 收款人解析 + 黑名单）
       ├─ billEngine.js    账单分析引擎（统计 / 评分制异常识别 / 订阅自动识别）
       ├─ wealthEngine.js  理财引擎（风险测评 / 适当性 / 推荐对比 / 持仓）
       ├─ giftEngine.js    跨场景联动引擎（对象·日期·预算识别 / 预算内选品）
       ├─ nlu.js           中文口语解析（金额 / 时间 / 分类 / 称谓）
       └─ llm.js           大模型网关（OpenAI 兼容，可开关）
```

技术选型要点：

1. **零第三方依赖**：`npm install` 秒过、`npm start` 一条命令启动，规避现场环境风险。
2. **双引擎容灾**：默认本地意图引擎，配置大模型后自动切换；大模型失败自动降级，演示不中断。
3. **密钥隔离**：大模型 API Key 仅由后端读取，前端代码零密钥引用。
4. **只监听本机**：服务仅绑定 127.0.0.1，局域网不可访问；静态资源做了目录穿越防护。

## 六、关键创新点

1. **安全即门禁**：适当性与风控不通过时，系统不生成确认入口——用户不会有机会"确认一个本来就不该发生的操作"。
2. **可验证合规**：每条安全机制都有自动化断言与界面证据支撑（含用独立进程读取磁盘以证明数据真落盘、异常识别独立复现预埋异常）。
3. **跨场景服务编排**：银行服务与本地生活服务打通，"锁定资金 → 下单 → 释放剩余 → 提醒"闭环，金额守恒、可撤销。
4. **意图路由的优先级设计**：预检优先于执行（"能不能转"≠"给我转"）、撤销优先于普通转账、取消订阅优先于订阅查询，避免一句话被错误的意图抢走。
5. **上下文承接与防劫持**：跨轮追问能承接上文（"下周三，五百左右，花和蛋糕都要"），同时在"没有其他意图命中 + 句子像补充信息 + 10 分钟内"三重条件下才接管，绝不劫持无关提问。
6. **诚实的能力边界**：对未实现或沙箱差异一律如实标注，系统中不存在"编造的执行结果"。

### 8.2 落地路径

1. **数据源接入**：把本地沙箱数据替换为行内客户、账户、账单、产品、订阅与黑名单数据（引擎接口已抽象）。
2. **执行通道接入**：动作层（`actions.js`）是唯一发生资金变动的地方，替换为行内核心系统或开放平台接口即可，确认与留痕逻辑无需改动。
3. **大模型合规接入**：可对接行内私有化大模型（本项目已支持 OpenAI 兼容协议，且默认具备离线降级能力）。
4. **风控策略运营**：10 条规则与阈值集中在配置中，可随行内策略调整，并保留每次判定的证据链。

## 十、边界与诚实声明

1. 本项目全部使用**本地沙箱数据**，不接入任何真实支付、银行、商户接口（界面常驻"沙箱演示环境"标识）。
2. **模拟短信验证码**在沙箱中直接显示并标注"真实环境由短信下发"，真实实现不会回显。
3. 理财赎回按 **T+0 到账**（沙箱加速），回执中明确标注真实环境为 T+1。
4. 办卡申请**仅到"审核中"**，不假装已发卡；定时转账**仅创建计划**，不模拟系统时间推进。
5. 所有未实现或受沙箱限制的能力一律如实标注，系统中**不存在编造的执行结果**。
