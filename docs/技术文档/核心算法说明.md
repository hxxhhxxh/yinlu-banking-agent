# 核心算法说明

> 配套文件：[系统架构图.png](系统架构图.png) / [系统架构图.svg](系统架构图.svg)
> 说明：本作品不使用深度学习模型做推理，**核心算法均为可解释的规则与统计方法**，每个判定都能给出证据；大模型（可选）只负责自然语言规划，不参与任何资金判定。

## 一、意图识别与路由

### 1.1 优先级路由（Rule Priority Routing）

**问题**：同一句话往往同时命中多个意图（"撤销最近一笔转账"含"转账"；"转账记录"含"转账"；"把那个老扣我钱的会员关了"含"会员"）。

**方法**：把意图规则做成**有序匹配列表**，命中即返回；顺序按"语义更具体者优先"设计：

| 优先级 | 规则 | 为什么必须排前面 |
| --- | --- | --- |
| 1 | 查询转账记录 | "转账记录"含"转账" |
| 2 | 转账风控预检 | "能不能转/有没有风险"问的是预检，不是执行 |
| 3 | 撤销最近一笔转账 | "撤销最近一笔转账"含"转账" |
| 4 | 定时转账 | "每月1号给房东转2200"含"给…转" |
| 5 | AA 拆分收款 | "跟室友AA"常与"转"共现 |
| 6 | 智能转账 | 兜底转账语义 |
| 7 | 异常识别 | "不对劲/被盗刷"要与账单分析区分 |
| 8 | 账单分析 | 排在异常识别之后 |
| 9 | 取消订阅 | "老扣我钱的**会员**"不能被"订阅查询"抢走 |
| 10 | 订阅查询 | —— |
| 11 | 持仓查询 | "我的理财"含"理财"，须排在推荐之前 |
| 12 | 理财推荐 → 测评 → 申购 → 赎回 | 申购必须晚于推荐，避免"买理财"被当成下单 |
| 13 | 卡片/跨场景/查询类 | 按语义具体度排列 |

### 1.2 可解释匹配度评分

**问题**：不能凭空给一个"置信度 95%"。

**方法**：分值由真实解析证据推导，并同时返回证据列表供界面展示：

```
score = 0.55
        + 0.15  (若唯一命中该意图)  − 0.05×min(命中数−1, 3)
        + 0.08  (提取到金额)
        + 0.08  (提取到消费分类)
        + 0.06  (提取到时间范围)
        + 0.05  (提取到日期)
        + 0.06  (提取到收款人线索)
        + 0.05  (触发关键词长度 ≥3) ；否则 −0.05
score = clamp(score, 0.30, 0.98)
```

**验证**：同一句输入两次得分一致；不同输入得分不同（自测断言）。

### 1.3 能力降级（Graceful Degradation）

当首选意图所属能力未上线、但存在"可先行的已实现能力"时，自动降级并**如实标注**：

```
if !implemented(primary.tool):
    alt = 命中列表中的已实现意图
    if !alt and primary.degradeTo 已实现:  alt = degradeTo 对应意图
返回 { rule: alt, degradedFrom: primary }   →  界面上显示"能力降级：X → Y"
```

**验证**：注入"仅 query_transactions 可用"的环境，验证降级链与来源标记同时生效。

### 1.4 上下文承接与防劫持

跨轮追问（"下周三，五百左右，花和蛋糕都要"）需要在无意图命中时被正确承接，但**不能劫持无关提问**。三重条件同时满足才接管：

```
1) 存在未完成的安排草稿，且 stage = asking 且 10 分钟未过期
2) 本句没有命中其他意图（resolvedRule 为空或就是该意图）
3) 句子"像在补充信息"：含数字/金额词/日期词/鲜花蛋糕等，且长度 ≤ 40
```

**验证**：`"储蓄卡还有多少钱"` 不被劫持（自测断言）。

## 二、中文口语解析

### 2.1 金额抽取（防噪音）

**问题**：`"每月1号给房东转2200房租"` 会先匹配到 `1`；`"尾号7742"` 会被当成 7742 元；`"4个人吃饭花了800"` 会取到 4。

**方法**：先剔除"非金额数字"，再取金额。

```
step1 剔除账号类： (尾号|卡号|账号|账户|手机号|手机|电话|工号)[\s:：]*([0-9＊*]{4,}(\s[0-9＊*]{4,})*)
      但若其后紧跟 元/块/块钱 则不剔除（那是金额）
step2 剔除日期时间与人数： (\d{1,2})月(\d{1,2})?[日号]? / (\d{1,2})[日号] / (\d{1,2})(点|点钟|时) / (\d{1,2})(周|星期) / (\d+)\s*个?人
step3 取金额：优先阿拉伯数字（含 w/k/万/千 单位换算），否则中文数字（十/百/千/万/亿 位值累加）
```

**验证**：4 组边界用例全部通过（尾号/日期/人数/单位）。

### 2.2 时间解析

- 相对日期：今天/明天/后天/大后天。
- 星期：`(下|这|本)?周([一二三四五六日天])`，按当前星期几计算偏移（"下周三"从 09-22 得 09-30）。
- 具体日期：`M月D日`、`D号`（若已过则顺延至下月）。
- **周期性日期优先**：`每月1号` 必须先判为周期性，否则会被当成"1号"从而误判为一次性转账。

**验证**："每月1号给房东转2200房租" → `{label:'每月1日', monthly:1}`。

### 2.3 预算解析（parseBudget）

**问题**：`"帮我安排一下"` 的"一"不是金额。

**方法**：金额必须带上下文标记才认定为预算：

```
主匹配： (数字|中文数字) 后紧跟 万|千|元|块|块钱|左右|以内|上下|出头
兜底匹配： 前面有 预算|大概|大约|约|差不多|不超过
```

**验证**：`"帮我安排一下"` → null；`"五百左右，花和蛋糕都要"` → 500。

### 2.4 分类 / 称谓 / 意愿识别

- **消费分类**：关键词映射表（吃饭→餐饮、打车→交通、缴费→生活缴费…），按关键词长度优先取最短歧义项。
- **收款人称谓**：`我妈/爸爸/室友/房东/同学` → 昵称；`给([\u4e00-\u9fa5]{2,4}?)(?=转|打|汇|发|送|付)` → 人名（非贪婪 + 后向断言，避免吞掉动词）。
- **服务意愿**：鲜花/蛋糕/都要三分类，用于跨场景选品。

## 三、风控规则引擎

### 3.1 规则集与特征

| 规则 | 特征条件 | 等级 |
| --- | --- | --- |
| R-09 收款人不存在 | 解析结果 status ≠ found | reject |
| R-01 不在常用名单 | `payee.usual === false` | strong |
| R-02 涉诈黑名单 | 账号尾号后缀匹配命中 | **block** |
| R-03 达到二次确认阈值 | `amount ≥ 5000` | confirm |
| R-04 夜间大额 | `(hour ≥ 23 或 hour < 6) 且 amount ≥ 1000` | confirm |
| R-05 整数大额 | `amount ≥ 10000 且 amount % 10000 == 0` | confirm |
| R-06 余额不足 | `amount > card.available`（给出差额） | reject |
| R-07 超单笔限额 | `amount > card.singleLimit` | reject |
| R-08 超当日累计 | `todayOut + amount > card.dailyLimit` | reject |
| R-10 高风险话术 | 备注命中诈骗词典或含催促词 | strong |

### 3.2 判定聚合

```
decision = block   if 存在 block 命中
         = reject  if 存在 reject 命中
         = confirm if 存在 confirm 或 strong 命中
         = allow   否则
```

即：**硬阻断 > 业务拒绝 > 二次确认 > 直接执行**。规则目录（`RULE_CATALOG`）是规则数量的唯一来源，自测会校验"声明条数 = 实际执行条数"，从机制上禁止写死。

### 3.3 收款人解析（5 级匹配）

```
1) payeeId 精确
2) 昵称/姓名精确（我妈→王丽华）
3) 姓名包含式（唯一命中→found；多命中→ambiguous，返回候选）
4) 手机号/账号尾号（≥4 位后缀匹配）
5) 备注线索（买菜/房租/生活费 → 收款人）
未命中 → not_found（不编造账户）
```

### 3.4 高风险话术识别

词典匹配（刷单/保证金/安全账户/解冻/垫付/验证资金/征信/公检法/客服退款）+ 催促性话术正则（`催|急|马上|立刻|尽快|赶紧`）作为社工特征提示。

## 四、异常交易识别（评分制）

### 4.1 特征与权重

| 特征 | 条件 | 权重 |
| --- | --- | --- |
| 深夜大额 | 时刻 ∈ [23:00, 06:00] 且金额 ≥ 1000 | +30 |
| 深夜小额 | 同时段且金额 ≥ 300 | +15 |
| 境外交易 | 交易地 = 境外 | +20 |
| 异地大额 | 交易地 ≠ 常用地 且金额 ≥ 1000 | +25 |
| 异地小额 | 交易地 ≠ 常用地 且金额 ≥ 300 | +10 |
| 金额突增 | 金额 ≥ 5×该分类中位数 且 ≥ 500 | +35 |
| 超大额 | 金额 ≥ 10000 | +10 |

### 4.2 阈值与误报控制

- 判定阈值：`score ≥ 40` 列为异常；排序按分值降序。
- 基线使用**同分类中位数**而非均值（对极端值不敏感）。
- 实测：扫描 303 笔支出，命中 4 笔（得分 85 / 65 / 60 / 45），**与数据中预埋的 4 笔异常完全一致，零额外误报**。

### 4.3 复杂度

单次扫描 O(N)（N 为流水条数），分类中位数预计算 O(N log N)；303 笔流水实测毫秒级完成。

## 五、周期性扣费识别

### 5.1 三判据

按商户分组后同时满足：

```
1) 出现次数 ≥ 3
2) 金额稳定：所有出现金额一致（误差 < 0.01）
3) 间隔稳定：相邻间隔均值 ∈ [25, 35] 天，且每个间隔与均值偏差 ≤ 5 天
```

命中后给出依据（"近 5 次金额均为 ¥30.00，间隔约 31 天"）、累计已扣金额与推算的下次扣费日。

### 5.2 与已登记订阅合并

年度型订阅（一年仅扣一次）无法被周期模式识别，系统标注为「**已登记**」而非「已自动识别」——不夸大识别能力。

## 六、适当性匹配

### 6.1 匹配算法

```
isSuitable(userLevel, product):
    若 product.suitableFor 存在 → 白名单包含判定（权威）
    否则 → index(userLevel) ≥ index(product.riskLevel)   （等级序兜底）
```

### 6.2 风险测评评分

5 题（年龄 / 年收入 / 资金占比 / 投资经验 / 亏损承受度），每题 A~E 对应 1~5 分：

```
总分 5~25 → C1 ≤8 ；C2 ≤12 ；C3 ≤16 ；C4 ≤20 ；C5 >20
```

测评有效期一年；过期或缺失时**拒绝申购并引导重新测评**。

## 七、跨场景选品算法

### 7.1 预算内最大化

在预算 B 内挑选"鲜花 + 蛋糕"组合，使总价最大且不超过 B：

```
best = argmax{ f.price + c.price : f ∈ 鲜花, c ∈ 蛋糕, 总价 ≤ B }
若不存在 → 返回最低可行组合价，请用户调整预算
```

复杂度 O(|鲜花| × |蛋糕|)，服务目录为个位数，枚举即最优。
实测：B = 500 → 玫瑰礼盒 268 + 6 寸慕斯 218 = **486**，剩余 **14**（预留运费）。

### 7.2 送达可行性

需满足"活动日 − 今天 ≥ 1 天"（提前一天下单），否则要求改期。

## 八、动作层状态机（资金安全的关键）

```
pending --确认且验证码正确--> done        （执行，写入台账与审计）
pending --用户取消--------> cancelled     （写审计 result=cancelled）
pending --超时 2 分钟------> expired       （写审计 result=expired）
pending --验证码错误3次----> locked        （写审计 result=failed，防暴力尝试）
done    --重复提交--------> 拒绝（"已执行完成，请勿重复提交"）
```

一致性保证：

1. **创建待确认单不改变任何资金**（自测断言）。
2. **执行前二次校验**（卡状态、可用余额、单笔限额），失败则落 `failed` 审计并说明"未发生资金变动"。
3. **审计与对话记录立即落盘**（不等防抖），重启后审计编号连续不重号。
